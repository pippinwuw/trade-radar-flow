# trade-radar-flow 开发者技术文档

面向二次开发与维护的技术说明。产品概述与快速上手见仓库根目录 [README.md](../README.md)；给 Agent 的协作约束见 [AGENTS.md](../AGENTS.md)。

---

## 1. 系统定位

trade-radar-flow 是一套 **B2B 线索研究工作流**：

1. 主 Agent 协助制定获客策略（目标客户、搜索矩阵、排除、验证门槛、预算）。
2. 用户对策略 hash 做显式批准后，系统按轮执行本地化搜索 → 官网抓取 → 国家/联系人校验 → 单公司证据化分析。
3. Campaign 状态写入 SQLite，可从检查点恢复；触达内容与线索状态始终由人工审核，系统不自动发信。

技术栈：

| 层 | 技术 |
|----|------|
| API / 编排 | Node.js ≥ 22.19、TypeScript（ESM / NodeNext）、Express 5 |
| Agent | `@earendil-works/pi-agent-core` / `pi-ai` |
| 搜索 | Serper（Google 本地化） |
| 爬虫 | Python 3.12 子进程，stdin/stdout JSONL |
| 存储 | SQLite（Node 内置 `node:sqlite` / `DatabaseSync`，见 `src/storage/database.ts`） |
| 导出 | ExcelJS（无 COM / 无本地模板） |
| UI | `public/` 静态页 |

## 4. 架构总览

```text
浏览器 public/
        │
        ▼
  src/server.ts  (Express + 静态资源)
        │
        ├─► orchestrator/service.ts     会话 / 策略审批 / 执行调度
        │         │
        │         ├─► main-agent.ts     CampaignOrchestratorAgent
        │         └─► pipeline.ts       按轮执行
        │                   │
        │                   ├─ discovery/   Serper + 去重 + 停止
        │                   ├─ crawler/     进程内 Node 抓取
        │                   ├─ validation/  国家 / 联系人
        │                   └─ agents/      CompanyAnalysisAgent（每域名独立）
        │
        ├─► market/         CountryProfile + MarketPolicy 生命周期
        ├─► storage/        SQLite 检查点与缓存
        └─► export/         Campaign JSON / XLSX
```

设计原则：

- **确定性逻辑在代码里**：预算、去重、停止、校验、持久化，不依赖模型散文。
- **一公司一上下文**：禁止跨 Lead 共享网页证据或模型消息。
- **证据可审计**：分析结论必须能落到当前 snapshot 的 `evidenceRef` / `contactRef`。
- **人工边界**：策略、MarketPolicy、最终触达均需人类批准。

## 5. 端到端主流程

```text
createSession
  → chat（策略草稿 / 国家 / MarketPolicy）
  → present_strategy_for_approval
  → approveStrategy(strategyHash)          # 人类
  → startExecution / runApprovedStrategy
       每轮:
         executeDiscoveryRound
           → Serper 搜索（带 exclusion 过滤器）
           → crawlCandidate（域名缓存）
           → validateCompanyCountry / validateContactCandidates
           → processCandidate → analyzeCompany
           → database.saveCampaign         # 检查点
         completeRound（低产出饱和则停该查询组）
  → analyzeCampaign / 报告
  → confirmReport → completed
  → export.json / export.xlsx
```

| 阶段 | 关键入口 | 文件 |
|------|----------|------|
| 会话 | `OrchestratorService.createSession` | `src/orchestrator/service.ts` |
| 策略模板 / hash | `createInitialStrategy`、`strategyHash`、`clampStrategy` | `src/orchestrator/strategy-template.ts` |
| 主 Agent | `CampaignOrchestratorAgent.chat` | `src/orchestrator/main-agent.ts` |
| 审批 | `approveStrategy` | `service.ts` |
| 执行 | `startExecution` → `runApprovedStrategy` | `service.ts` + `pipeline.ts` |
| 发现一轮 | `executeDiscoveryRound` | `src/discovery/discovery-service.ts` |
| 抓取 | `crawlCandidate` | `src/crawler/index.ts` |
| 公司分析 | `AgentRuntime.analyzeCompany` | `src/agents/pi-agent-runtime.ts` |
| 续跑 | `resumeExecution`（同 `campaignId`） | `service.ts` / `pipeline.ts` |
| 导出 | `projectCampaignExport` | `src/export/campaign-export.ts` |

旁路入口（不走完整编排对话）：

- `runOfflineSampleCampaign` — UI「离线验证样例」，强制 demo runtime
- `runSearchCampaign` / `runManualCampaign` — 直接搜索 / 分析 API

## 8. Agent 系统

### 8.1 Runtime 选择

`pipeline.getAgentRuntime()`：

- `PI_AGENT_MODE=live` → `PiAgentRuntime`
- `PI_AGENT_MODE=demo` → `DemoAgentRuntime`（`demo-data.ts`，无网络 / 无模型 API）

接口（`src/agents/agent-runtime.ts`）：`planSearch`、`analyzeCompany`。

### 8.2 三类 Agent

| Agent | 职责 | 实现位置 |
|-------|------|----------|
| **CampaignOrchestratorAgent** | 策略协作、国家/政策、预览查询、送审、报告、失败续跑 | `orchestrator/main-agent.ts` |
| **SearchPlanningAgent** | 生成查询预览（`submit_search_plan`），不真正搜索 | `PiAgentRuntime.planSearch` |
| **CompanyAnalysisAgent** | 单域名尽调；读证据后 `submit_company_analysis` | `PiAgentRuntime.analyzeCompany` |

生产 prompts **只改** `src/agents/production-prompts.ts`（`ORCHESTRATOR_SYSTEM_PROMPT`、`COMPANY_ANALYSIS_SYSTEM_PROMPT`、`searchPlanningSystemPrompt` 等）。改公司分析契约时同步：

- `COMPANY_ANALYSIS_CONTRACT_VERSION`（`analysis/company-context.ts`）
- `validateAndNormalizeCompanyAnalysisV2`（`validation/company-analysis-validator.ts`）

### 8.3 工具边界（必须遵守）

**公司分析侧**：`get_company_context_manifest`、`get_company_evidence_pack`、`search_company_evidence`、`read_evidence_context`、`get_contact_candidates`、`submit_company_analysis`。

- 事实引用必须使用当前 snapshot 的 **`evidenceRef`**。
- 联系人使用独立 **`contactRef`**；禁止模型手抄/猜测邮箱电话。
- 搜索摘要、旧资格结论 **不是** 官网证据。

**编排侧**：按 session 状态暴露策略读写、MarketPolicy、预览、送审、报告等工具；Agent **不得**自行批准策略或政策，不得自动外发触达。

上下文编译：`analysis/context-manager.ts` 的 `compileContext`；required 段（系统规则、已批策略、已引用证据）不可被静默截断。

## 9. Discovery

关键文件：`discovery-service.ts`、`query-planner.ts`、`query-exclusions.ts`、`serper-client.ts`。

一轮大致步骤：

1. 使用已批准策略中的查询（或 `planCampaignSearch` 规划结果）。
2. 绑定 **approved** `MarketPolicy`（`buildCampaignAgentContext`）。
3. `buildEffectiveSearchQuery`：追加 `-site:`（最多 12）与品牌排除（最多 8），总长预算约 1000 字符。
4. `SerperClient.search`（`gl` / `hl` / `location` 来自 CountryProfile；结果可进 `search_cache`）。
5. `isExcludedSearchHit` + Campaign 内域名去重。
6. 并发 `crawlCandidate` → 国家 / 联系人校验 → 进入分析队列。

停止条件（见 `pipeline.completeRound`）：

- `max_queries`：预算用尽
- `all_groups_saturated`：连续低产出轮次达到阈值（默认连续 3 轮；新域名数 / 比率过低）
- `plan_exhausted`：计划查询耗尽
- `failed`：可检查点后续跑

## 10. 爬虫（进程内 Node）

### 10.1 入口

`crawlCandidate`（`src/crawler/index.ts`）负责缓存与 in-flight 去重，实际抓取在
`src/crawler/crawl.ts`。不再启动 Python 子进程。

### 10.2 边界与安全

必须保留：

- 仅 http/https；拒绝 URL 内嵌凭据
- DNS 后拒绝 private / loopback / link-local 等（SSRF）
- 手动跟随重定向并每跳复查
- 非 HTML、超大响应拒绝（`CRAWLER_MAX_HTML_BYTES`）
- 域名级 deadline

抽取：同站业务页递归、正文清洗（可选 regex）、公开 `contactCandidates`。
编排与业务决策不要塞进抓取层。

### 10.3 缓存

`crawlCandidate` 缓存键：domain + maxPages + regexCleaning；TTL = `CRAWLER_CACHE_TTL_DAYS`。

## 11. MarketPolicy

### 11.1 文件布局

```text
market-policies/<marketId>/
  profile.json
  active.json                    # 指向当前版本 + hash
  versions/<version>/policy.json

data/market-policies/            # 运行时草稿 / 本地批准（勿提交）
  drafts|approved|profiles/...
```

Schema：`market-policies/schema/*.schema.json`。  
内置市场示例：`uae`、`saudi`。

### 11.2 生命周期

```text
draft → reviewed → approved → superseded
```

- Agent 可生成草稿并 `review`。
- **仅用户**可 `approve`。
- SQLite `market_policy_versions` 只存版本、hash、status、路径、审批元数据；**规则正文只在文件里**。

关键符号：`saveMarketPolicyDraft`、`markMarketPolicyReviewed`、`approveMarketPolicy`、`getApprovedMarketPolicy`、`marketPolicyRef`（`src/market/policy.ts`）。

新国家：编排工具 `set_target_country` / `submit_market_profile` → 保守草稿 → 用户批准后可搜索。

## 12. 持久化与检查点

`src/storage/database.ts` 是 Campaign / 会话 / 缓存的真相源。对话状态在 SQLite，**不要**改成 JSONL 对话库；`logs/` 仅审计。

| 概念 | 用途 |
|------|------|
| `campaigns`（`result_json`） | Campaign 全量检查点（含 discovery 进度） |
| `leads` | 线索投影 |
| `orchestrator_sessions` / `orchestrator_messages` | 编排会话 |
| `strategy_versions` | 策略版本与批准时间 |
| `market_policy_versions` | 政策元数据 |
| `search_cache` / crawl 缓存 | Serper 与域名抓取复用 |
| `company_analysis_cache` | 严格指纹的分析缓存 |
| `company_evidence_indexes` | 证据索引 |
| `agent_runs` / `crawl_snapshots` / `search_runs` | 审计切片 |

每轮 discovery / analysis 后 `saveCampaign`。`resumeExecution` 复用原 `campaignId`，已分析域名跳过。

## 13. 分析、校验与导出

### 分析

`buildCompanyContext`（`analysis/company-context.ts`）构造域名级证据包、索引与 cacheKey（含 policy hash、模型、契约版本）。  
`compileContext` 按信任度 / 优先级投影进 prompt。

### 校验

| 模块 | 作用 |
|------|------|
| `company-analysis-validator.ts` | `evidenceRef` 必须已读且 quote 可定位；规范化分析结果 |
| `country-validator.ts` | 域名 / 电话 / 地址等国家信号 |
| `contact-validator.ts` | 语法、MX、同域、号码格式等 |

### 导出

`CAMPAIGN_EXPORT_SCHEMA_VERSION = 1`。  
`projectCampaignExport` → JSON；`buildCampaignWorkbook` → 工作表：Campaign Summary / Leads / Evidence / Contacts。  
不读取 `doc/target/` 或任何客户本地模板；单元格文本做公式注入转义。

## 15. 安全不变量（改代码时勿破坏）

1. 默认监听 `127.0.0.1`；无鉴权，勿直接暴露公网。
2. 保留爬虫 SSRF、重定向、类型与体积检查。
3. 网页正文、SERP、模型输出均为不可信数据；防 prompt injection。
4. 一公司一独立 Agent 上下文；禁止跨 Lead 共享证据或消息。
5. 官网事实只认当前 snapshot 的 `evidenceRef`；联系人只认 `contactRef`。
6. 策略与 MarketPolicy 变更必须人类批准；不得静默扩大已批预算后执行。
7. 不得自动发送 Email / WhatsApp。
8. `demo` 与离线样例路径保持零外网、零模型计费。
9. 勿提交 `.env`、DB、logs、`data/market-policies`、真实客户表 / 导出。
10. 日志勿记录完整网页、联系人明文、密钥、完整 prompt 或隐藏推理。

安全漏洞私下报告流程见 [SECURITY.md](../SECURITY.md)。

## 16. 扩展指南

### 16.1 新增内置市场

1. 在 `market-policies/<marketId>/` 添加符合 schema 的 `profile.json`、`versions/<v>/policy.json`、`active.json`（hash 一致）。
2. 重启后由 `market/registry.ts` + `ensureMarketPolicies()` 加载。
3. 或运行时走 Agent 草稿 → 用户 approve（写入 `data/market-policies/`）。

### 16.2 修改 Prompts

只编辑 `src/agents/production-prompts.ts`。保持证据标准与人工审批边界；契约变更同步 contract version 与 validator，并补测试。

### 16.3 新增 HTTP API

- 路由挂在 `server.ts`
- 业务进 `OrchestratorService` / `pipeline` / 对应子系统
- 持久化走 `getDatabase()`
- 用户可见错误优先中文

### 16.4 新增 Agent 工具

- 编排：在 `CampaignOrchestratorAgent` 注册，并按 session status 裁剪可见工具集。
- 公司分析：在 `PiAgentRuntime.analyzeCompany` 增加；提交结果仍须经过 `validateAndNormalizeCompanyAnalysisV2`。
- 新共享类型放入 `domain.ts`。

### 16.5 改爬虫

改 `src/crawler/` 下的抓取、SSRF 或抽取，并跑 `npm test`。不要再引入 Python worker。
